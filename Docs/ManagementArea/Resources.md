> **상태**: ✅ 구현 완료 — 지갑(`ResourceWallet`) + 생산처(`ResourceProductionSource`) + 통합 테스트 하네스(`ManagementTest`)

이 문서는 **이번 이슈(#42)에서 무엇을 만드는지**(범위·설계·계약)와, 이후 **무엇이 만들어졌는지**를

떠받치는 토대다.

## 1. 이번 이슈에서 만드는 것 (Scope)

이번 이슈(#42)는 자원 흐름의 **입구(생산처)** 와 **저장소(지갑)** 두 조각을 만든다.

### 1-A. 런타임 자원 지갑 (Wallet) — ✅ 구현 완료

게임 진행 중 현재 보유한 자원의 상태를 보관하고 획득·소비·질의하는 단일 창구.

- **보유량 보관**: 4종 자원(나무/철/식량/마나석)의 현재 수량을 런타임 상태로 유지
- **획득**: 외부 시스템이 발생시킨 자원을 지갑에 더한다
- **소비**: 자원을 차감한다. 보유량이 부족하면 차감하지 않고 실패로 알린다
- **질의**: 현재 보유량 조회, 특정 비용을 감당 가능한지 판정
- **변경 통지**: 보유량이 바뀔 때 관심 있는 시스템(UI 등)에 알린다

자원의 **종류(Kind)** 는 muchan의 DataTable 정의(`ResourceKind`: `Wood`/`Iron`/`Food`/`Mana`)를
그대로 식별자로 사용한다. 지갑은 자원 정의를 새로 만들지 않는다.

### 1-B. 생산처 (Production Source) 코어 + 경계 심(seam) — ✅ 구현 완료

주민을 배치해 자원을 생산하는 건물(GDD §6.1)의 **런타임 생산 단위**(`ResourceProductionSource`).
muchan의 `BuildingAsset.ProductionFields`(`BaseAmountPerVillager`, `OutputResource`)를 입력 데이터로,
배치된 주민 수를 곱해 생산량을 산출하고 그 결과를 **지갑에 `Add`** 한다.

- **생산량 계산**: `BaseAmountPerVillager × 배치 주민 수` → 어떤 `ResourceKind`를 얼마 생산하는지 산출
- **정산 실행**: 산출된 자원을 지갑에 넣는다 (지갑의 유일한 "위(생산)" 공급원)
- **자원 매핑**: `OutputResource`(`ResourceAsset`) → `ResourceData.Kind` → 지갑 키로 변환
- **건물 필터**: `TryCreate(BuildingAsset, ...)`가 자원 생산 건물이 아닌 것(비-Production 타입 /
  훈련장(`ProducesSoldier`) / `OutputResource` 미지정)을 걸러낸다.

> **의존이 아직 없으므로 경계는 심(seam)으로 둔다** (§3.5):
> - **주민 수**는 생산처가 소유하지 않고 **외부에서 입력**받는다 (주민 시스템 부재 — 후속).
> - **정산 시점**은 생산처가 스스로 정하지 않고 **외부 호출**로 트리거된다 (낮/밤 시스템 부재 — 후속).

### 1-C. 통합 테스트 하네스 (`ManagementTest`) — ✅ 구현 완료

없는 주민·낮/밤 시스템을 키 입력으로 흉내 내어 두 경계 심을 손으로 구동하는 개발 전용
MonoBehaviour(`Management/scripts/Test/`). 자세한 내용은 §5. 실제 게임 코드가 아니라 **심 검증용**이며,
주민·낮/밤 시스템이 생기면 이 하네스가 그 자리를 대체한다.

## 2. 이번 이슈에서 만들지 않는 것 (Out of Scope — 후속 이슈)

경계를 분명히 해 자원 시스템이 과도한 책임을 갖지 않도록 한다.

- ❌ **주민 시스템**: 주민 보유·배치·집계·초기화 (GDD §6.1). 현재 부재 — 생산처는 주민 수를
  외부 입력으로만 받는다.
- ❌ **낮/밤 정산 훅**: 낮→밤 자원 정산 트리거, 밤→낮 초기화 연동 (팀 계약 #5). 현재 부재 —
  생산처 정산은 외부 호출로 트리거된다. 페이즈 시스템 확정 시 이 호출부를 붙인다.
- ❌ **비용 소비처**: 건물 건설·타워 강화·병사 훈련 등 실제 차감 호출부. 각 시스템이 지갑의
  `TrySpend`/`CanAfford`를 호출한다.
- ❌ **건물 배치/건설**: 생산처 인스턴스를 씬에 놓고 주민을 배치하는 UI·흐름.
- ❌ **UI/HUD**: 자원 표시 위젯. `OnChanged` 이벤트를 구독해 후속 이슈에서 구현.
- ❌ **세이브/로드 영속화**.

## 3. 설계

### 3.1 책임 경계 (팀 계약 #6)

> 배치 판정 = 그리드/검증, **자원 차감 = 경영 시스템**, 정보 표시 = UI.

이 지갑이 곧 "경영 시스템의 자원 차감/보관 창구"다. 다른 시스템은 지갑을 통해서만
자원을 더하거나 뺀다. 지갑은 **얼마를 왜 벌고 쓰는지(생산 규칙·비용 규칙)를 모른다** —
그건 각 소비/생산 시스템의 책임이다.

### 3.2 자원 흐름 고정 (팀 계약 #3 / GDD §4.2)

지갑은 우회 경로를 만들지 않는다. 자원의 획득 출처는 GDD가 고정한 채널(주민 배치 생산,
영토 확장·전투 보상)뿐이며, 지갑은 그 결과를 받아 담는 그릇일 뿐이다. `Add`는 공개 API지만
"어떤 시스템이 왜 호출하는가"는 자원 흐름 규칙을 지켜야 한다.

### 3.3 시스템 내 위치 (아키텍처 역할)

지갑은 경영 시스템의 **자원 상태 저장소이자 단일 게이트웨이**다. 위·아래로 두 부류의
시스템과만 만난다.

```
[자원을 버는 쪽]                    [자원을 쓰는 쪽]
 · 생산(주민 배치 결과)      획득 →   · 건물 건설
 · 영토 확장 보상          ┌─────────┐   · 타워 강화
 · 전투 보상          ────▶│ 자원 지갑 │◀────  · 병사 훈련
                          └─────────┘   · 스킬 획득(마나석)
                            │  소비 →
                    변경 통지 │
                            ▼
                       [UI / 표시]
```

- **위(생산)**: **생산처**가 "얼마가 벌렸다"는 결과만 지갑에 넣는다. 지갑은 생산 규칙을 모른다.
- **아래(소비)**: 각 소비처가 "얼마가 필요하다"를 지갑에 묻고 차감을 요청한다. 지갑은 비용 규칙을 모른다.
- **옆(표시)**: 지갑은 변경 사실만 통지하고, 표현은 UI가 맡는다.

즉 지갑의 유일한 관심사는 **"지금 얼마 있고, 더하고 뺄 수 있는가"** 이며, 벌고 쓰는 *이유*는
전부 경계 밖에 있다. 이 좁은 책임이 팀 계약 #3·#6을 코드 레벨에서 강제하는 지점이다.

### 3.4 생산처의 위치 (아키텍처 역할)

생산처는 위 그림에서 **"위(생산)" 화살표의 이번 이슈 구현체**다. 자원 흐름의 입구이며, 지갑과
반대로 **"왜·얼마 버는가"의 규칙(주민당 생산량 × 주민 수)** 을 아는 쪽이다. 단, 규칙의 두 입력을
스스로 소유하지 않는다.

```
[정적 데이터]              [이번 이슈: 생산처 코어]           [지갑]
 BuildingAsset      ┌──────────────────────────────┐
  .ProductionFields ─▶│ 생산량 = 주민당량 × 주민 수     │
  (주민당 생산량,     │ OutputResource → ResourceKind │── Add(kind, 양) ─▶ 자원 지갑
   OutputResource)   └──────────────────────────────┘
                          ▲                  ▲
              (주민 수)    │      (정산 트리거)  │
        [외부 입력 — 주민 시스템 후속]   [외부 호출 — 낮/밤 시스템 후속]
```

- 생산처는 **정적 데이터(건물)** 를 읽어 규칙을 알고, **런타임 입력(주민 수)** 을 받아 계산하며,
  **정산 시점(외부 트리거)** 에 결과를 지갑에 넣는다.
- 두 점선 입력이 이번 이슈의 **경계 심(seam)** 이다. 주민·낮/밤 시스템이 생기면 이 심에 연결만 하면 된다.

### 3.5 경계 심(seam) 설계 원칙

주민·낮/밤 시스템이 부재하므로, 생산처는 그 둘을 **가정하거나 스텁으로 흉내 내지 않고 경계로 노출**한다.

- **주민 수 = 입력 파라미터**: 생산처는 "주민이 몇 명인지"를 저장·관리하지 않는다. 생산량을 계산할 때
  호출자가 주민 수를 넘긴다. 주민 시스템이 생기면 그 값의 출처만 바뀐다.
- **정산 = 외부 트리거**: 생산처는 "언제 생산할지"를 스스로 정하지 않는다. 외부(현재는 테스트/수동,
  후속엔 낮→밤 전환 훅)가 정산을 호출한다. 팀 계약 #5의 전환 이벤트 구조에 그대로 얹힌다.
- 이렇게 하면 이번 이슈 결과물이 **주민·낮/밤 설계를 선점하지 않는다** (SystemMap §5 미결 존중).

### 3.6 상태 특성

- **런타임 전용**: 지갑은 진행 중 게임 상태다. 자원 종류·표시명 같은 정적 정의(DataTable)와 분리된다.
- **단일 진실 원천**: 자원 보유량은 지갑 한 곳에만 존재한다. 다른 시스템이 자체 사본을 두지 않는다.
- **씬 범위 시작**: 전역 매니저 수명주기가 미결(SystemMap §5)이므로 우선 경영 씬 범위로 시작하고,
  부트스트랩 확정 시 재검토한다.

## 4. 통합 계약 / 미결 사항

- **muchan `ResourceKind` 의존**: 지갑 키가 `ResourceKind` enum이므로 이 enum이 곧 공유 타입이 된다.
  현재 전역(Assembly-CSharp)이라 참조 가능. muchan이 enum을 바꾸면 지갑이 영향받는다(접점).
- **muchan `BuildingAsset.ProductionFields` 의존**: 생산처가 `BaseAmountPerVillager`·`OutputResource`를
  입력으로 읽는다. muchan이 이 필드 구조를 바꾸면 생산처가 영향받는다(접점).
- **`ResourceAsset → ResourceKind` 매핑(이번 이슈 실동작)**: `OutputResource`는 `ResourceAsset`인데
  지갑은 `ResourceKind` 키다. 생산처가 정산 시 `ResourceData.Kind`로 변환해야 한다. `ResourceAsset.Data`는
  호출부가 `Start()`에서 채우는 규약(SystemMap §2)이므로, 생산처는 `Data`가 채워졌다는 전제/방어가 필요하다.
- **비용 표현 불일치(소비처 후속)**: muchan의 `ResourceCost`도 `ResourceAsset` 기반 — 위 매핑과 동일 문제.
  구매 판정·차감 호출부(건물 건설/타워 강화)는 소비처 이슈에서 같은 변환을 쓴다.
- **주민 수 입력 심**: 주민 시스템 부재 — 생산처는 주민 수를 외부 입력으로 받는다(§3.5). 주민 시스템
  이슈에서 이 입력의 출처를 연결.
- **정산 트리거 심**: 낮/밤 시스템 부재 — 정산은 외부 호출로 트리거(§3.5). 페이즈 시스템 이슈에서
  낮→밤 전환 훅에 연결(팀 계약 #5).
- **수명주기**: static / DontDestroyOnLoad / 씬 싱글톤 혼재(SystemMap §5). 우선 씬 단위로
  시작하되 부트스트랩 확정 시 재검토.
- **초기 보유량**: 게임 시작 시 기본 자원값 출처(하드코딩 vs 데이터) 미정 — 후속.

## 5. 검증 방법 (테스트 하네스)

지갑·생산처는 순수 로직이라 원래 EditMode 유닛 테스트에 이상적이지만, **이 프로젝트는 asmdef가
전혀 없다**(전부 Assembly-CSharp — SystemMap §5). Unity의 EditMode 테스트는 test asmdef가 필수인데
**asmdef는 Assembly-CSharp를 참조할 수 없어**, 유닛 테스트가 `ResourceWallet`·`ResourceKind`·
`ResourceAsset` 등을 볼 수 없다. 진짜 유닛 테스트는 프로젝트가 asmdef를 도입(팀 합의)한 뒤에 가능하다.

그래서 이번 이슈는 팀 관행(MonoBehaviour 테스트 + 씬 Play 확인, SystemMap §6)대로
**`ManagementTest` 하네스**로 검증한다. `ManagementSystem` 씬의 `ManagementTester` 오브젝트에 붙어 있고,
`_resourceAssets`에 `ResourceID`가 CSV(`wood`/`iron`/`food`/`mana`)와 일치하는 `ResourceAsset`을 할당한 뒤
Play(또는 `unity-cli editor play`)로 실행한다.

**조작 / 심 구동**

- **숫자키 1~N**: 해당 생산 라인에 주민 +1 (낮에만) — 주민 수 입력 심
- **Shift + 숫자키**: 해당 라인 주민 -1 회수
- **Space**: 낮/밤 전환 — 정산 트리거 심. 단, 배치 합계가 `maxVillagers`에 못 미치면(잉여 주민)
  전환을 막고 로깅한다. 낮→밤에 각 라인 `Produce` 실행, 밤→낮에 배치 초기화(팀 계약 #5)
- 모든 단계와 `[지갑 총액]`이 `Debug.Log`로 남아 흐름을 눈으로 확인한다.
  `AssignVillager`/`UnassignVillager`는 public이라 후속 생산 라인 패널의 +/- 버튼이 그대로 호출 가능.

**하네스로 확인하는 행동 계약**

- 지갑: 획득 시 정확히 증가 / 부족 소비 거부(잔액 불변) / 정상 소비 차감 / 값 변경 시에만 통지
- 생산처: `주민당량 × 주민 수` 정확(주민 0 → 0) / 정산 시 올바른 `ResourceKind`로 지갑에 Add /
  정산 미호출 시 지갑 불변(심 검증) / 비생산 건물·훈련장은 `TryCreate` 거부
