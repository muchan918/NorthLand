# MouseManager 설계 문서

게임 내 **모든 마우스 클릭/포인터 입력**을 한 곳에서 처리하는 중앙 매니저의 설계 문서.
개발 중 마우스 상호작용(오브젝트 배치, 선택, 패널 열기 등)을 구현·확장할 때 참고 용도로 쓴다.

- 관련 이슈: **#9**
- 프로젝트는 신규 Input System(`InputSystem_Actions.inputactions`)을 사용한다.
- `Assets/Scripts`에는 아직 코드가 없으므로, 아래 코드는 **구현 전 제안 스켈레톤**이다. 실제로 구현/변경한 사람은 이 문서도 함께 갱신해 문서와 코드가 어긋나지 않게 유지한다.

> ⚠️ 세부 요소(하이라이트 연출, 2D/3D 레이캐스트, 그리드 스냅 방식 등)는 **아직 확정되지 않았다.**
> 확정 전까지는 이 문서의 관련 항목을 "제안/TBD"로 읽고, 결정되면 이 문서를 업데이트한다.

## 1. 목적 · 핵심 원칙

**단일 책임**: 마우스/포인터 입력을 읽고(위치·클릭), 월드 레이캐스트를 수행하고, 클릭 결과를 라우팅하는 것은
`MouseManager` **하나만** 담당한다.

- 다른 컴포넌트는 `Mouse`/`Input`을 직접 읽지 않는다.
- 클릭에 반응하고 싶은 오브젝트는 **인터페이스(`ISelectable`)를 구현**하거나 **이벤트를 구독**한다.
- 배치를 시작하고 싶은 UI/시스템은 **`MouseManager`에 배치 요청(`PlacementRequest`)을 넘긴다.**

이렇게 하면 입력 처리 지점이 한 곳으로 모여, 입력 버그를 추적하기 쉽고 새로운 상호작용 모드를 추가하기 쉽다.

## 2. 책임 범위

| 담당함 (MouseManager) | 담당하지 않음 (다른 시스템) |
|---|---|
| 포인터 위치·좌/우클릭 감지 | 배치 가능 여부 판정 규칙 → **그리드/검증 시스템** |
| UI 위 클릭인지 월드 클릭인지 구분 | 어떤 정보 패널을 어떻게 그릴지 → **UI 시스템** |
| 월드 레이캐스트 및 히트 오브젝트 판별 | 타워/건물/병사의 실제 생성·능력치 → **각 배치물 시스템** |
| 현재 상호작용 모드(상태) 관리 | 자원 차감·해금 조건 → **경영/자원 시스템** |
| 선택/배치 결과를 이벤트·콜백으로 전달 | |

## 3. 상태 구조 (State Machine)

현재 필요한 상태는 두 가지. 향후 스킬 타겟팅 등은 새 상태로 추가한다(→ 6. 확장 포인트).

```
        BeginPlacement(request)
   ┌───────────────────────────────►┐
   │                                 │
┌──┴───────────┐               ┌─────▼────────┐
│     Idle     │               │  Placement   │
│  (선택 모드) │               │  (배치 모드) │
└──┬───────────┘               └─────┬────────┘
   │  ▲                               │
   │  └───────────────────────────────┘
   │    · 유효 셀 좌클릭 → 배치 후 복귀
   │    · 우클릭 / Esc  → 취소 후 복귀
   │
   └─ 좌클릭: 배치물 히트→선택 / 빈 곳 히트→선택 해제
```

- **Idle (선택 모드, 기본)**: 좌클릭으로 배치된 오브젝트를 선택하거나 선택을 해제한다.
- **Placement (배치 모드)**: 고스트(프리뷰)가 마우스를 따라다니고, 유효한 위치에서 좌클릭하면 배치한다.

## 4. 시나리오별 흐름

### 4.1 오브젝트 배치 (요구사항 ①)

예: UI 패널에서 타워를 고르면 → 프리뷰가 마우스를 따라다니고 → 배치 가능한 곳에서 클릭하면 배치.

1. 플레이어가 UI 빌드 패널에서 타워 버튼을 클릭한다.
2. 버튼 핸들러가 `MouseManager.BeginPlacement(request)`를 호출한다.
   `request`에는 **고스트 프리팹**, **배치 가능 판정 함수**, **배치 확정 콜백**이 담긴다.
3. `MouseManager`가 `Placement` 상태로 전환하고 고스트 프리뷰를 생성한다.
4. 매 프레임: 포인터 위치 → (그리드 스냅) → 고스트 이동, 검증 함수로 유효 여부 질의 → 유효/무효 시각화(*하이라이트: TBD*).
5. **좌클릭 시**
   - 포인터가 UI 위 → 무시
   - 유효한 셀 → 배치 확정(`request.OnConfirmed`) 후 고스트 제거, `Idle` 복귀 *(연속 배치 여부는 TBD)*
   - 무효한 셀 → 배치 거부 피드백, `Placement` 유지
6. **우클릭 / Esc** → 배치 취소, 고스트 제거, `Idle` 복귀.

### 4.2 배치된 오브젝트 선택 → 패널 표시 (요구사항 ②)

1. `Idle` 상태에서 좌클릭.
2. 포인터가 UI 위면 → UI가 처리하고 월드 레이캐스트는 건너뛴다.
3. 월드 레이캐스트 결과:
   - `ISelectable` 히트 → 이전 선택 해제 후 새 오브젝트 선택 → `OnSelected()` 호출(해당 오브젝트가 자기 패널을 연다) + `OnSelectionChanged` 이벤트 발행.
   - 빈 공간/바닥 히트 → 선택 해제, 패널 닫기.

> `MouseManager`는 "어떤 패널을, 어떻게 여는지" 모른다. 선택 사실만 알리고(인터페이스/이벤트),
> 실제 패널 표시는 배치물 또는 UI 시스템이 담당한다 → 결합도를 낮춰 확장성 확보.

### 4.3 단일 책임 · 확장성 (요구사항 ③)

- **입력 읽기는 여기서만**: 다른 스크립트는 `Mouse.current`를 직접 읽지 않는다.
- 클릭 반응이 필요하면 → `ISelectable` 구현 또는 `MouseManager` 이벤트 구독.
- 배치가 필요하면 → `PlacementRequest`를 만들어 `BeginPlacement`에 전달.
- 새 상호작용 모드(예: 야간 스킬 타겟팅)는 → **새 상태만 추가**, 기존 코드 영향 최소화.

## 5. 확장 포인트

- **새 상호작용 모드**: 현재는 `enum Mode { Idle, Placement }`로 충분하지만, 모드가 늘면
  `IMouseState`(Enter/Update/Exit) 기반 **State 패턴**으로 승격한다. 후보 모드:
  - **스킬 타겟팅**(야간, GDD 6.5): "스킬 선택 → 위치 지정 → 사용"도 배치와 같은 구조 → `TargetingState`로 추가.
  - **병사 배치**(GDD 6.4): 웨이포인트 위에서만 유효한 `PlacementRequest`로 재사용 가능.
  - **경영 영토 확장**(GDD 6.3): 인접 노드 선택도 `ISelectable` + 전용 상태로 확장 가능.
- **배치물 종류 확장**: 타워/건물/병사가 늘어도 `PlacementRequest`의 `CanPlaceAt`/`OnConfirmed`만 다르게 구성하면 되고 `MouseManager` 본체는 그대로.
- **선택 반응 확장**: 새 배치물은 `ISelectable`만 구현하면 자동으로 선택·패널 흐름에 편입된다.
