## 1. 목표 룩 · 원리

**오쏘그래픽 카메라(확정) + 셰이더로 "움직이는 미니어처(디오라마)" 착시**를 만든다(2.5D보다 미니어처 우선 — 팀 결정).

실사 미니어처 착시는 사진학적으로 잘 알려진 조합이며, 효과 기여도 순으로:

| 순위 | 요소 | 기여도(체감) | 원리 |
|---|---|---|---|
| 1 | **틸트-시프트 블러** | ~50% | 좁은 포커스 밴드 + 상하 블러 = "접사로 찍은 작은 물체" 착시의 본체 |
| 2 | **컬러 그레이딩** | ~25% | 채도↑·대비↑·따뜻한 톤 = 장난감/점토 특유의 쨍한 색감 |
| 3 | **라이팅** | ~15% | "책상 스탠드" 같은 강한 단일 키 라이트 + 또렷한 그림자 |
| 4 | **SSAO·비네트** | ~10% | 접지 그림자가 "작은 물체" 스케일감, 비네트가 "탁상 위 디오라마" 프레임감 |
| - | 오브젝트 셰이더(툰) | **확정** | **그림자를 단조롭게 눌러 2D 느낌**을 주는 것이 채택 목적이다(2026-07-31). 형태 가독성·색 단순화 — Flat Kit 툰 머티리얼 |
| - | ~~아트 전역 아웃라인~~ | **미채택**(2026-07-31) | 전역 잉크 라인은 **하지 않는다**. 아웃라인은 **선택·호버된 대상에만** 쓴다 — §3.5 |
| - | (픽셀레이션) | **보류 · 실물 확인 후 결정** | 도트 룩 방향. 문서로 정하지 않고 **프로토타입을 화면으로 보고** 판단한다 — §3.7 |

> **아웃라인은 상호작용 전용이다.** 상시로 깔리는 아트 라인이 없으므로, 화면에 아웃라인이 보이면
> **100% "선택 또는 호버"를 뜻한다.** 시각 언어 충돌을 걱정할 필요가 없어져 색·두께 자유도가 커졌다(§3.5·§3.6).

## 2. 확정 결정 (팀 결정, 2026-07-21 — 이슈 #148)

1. **오쏘그래픽 카메라 확정.** 룩 전체의 전제 — 아래 결정은 모두 오쏘를 전제로 한다.
2. **틸트-시프트 = 스크린 Y 밴드 방식(자작 풀스크린).** URP 빌트인 DoF는 **오쏘 카메라 미지원**(공식 문서 명시)이라 제외.
   화면 세로축 기준 포커스 밴드 + 상/하 그라데이션 블러 — 원조 틸트-시프트 사진과 동일 원리이며
   고정 쿼터뷰 구도에 최적, 아트 컨트롤(밴드 위치/폭/강도) 용이.
3. **오브젝트 셰이딩 + 아웃라인 = Flat Kit**(에셋 스토어 `Flat Kit: Toon Shading and Water`, `Assets/Imported/` 벤더 배치).
   근거: Unity 6000.3/URP 17.3 지원 범위 안 + **활발한 유지보수**(v4.9.11, 2026-06 — 공식 툰 셰이더의 방치 리스크 회피),
   아웃라인이 **URP 렌더러 피처(스크린 스페이스)**라 우리가 원한 전역 방식이면서 틸트-시프트와 같은 계열. 물 셰이더도
   포함되나 muchan `WaterURP_Ortho`가 이미 있어 **미사용**. 남은 검증: **오쏘 카메라에서 Flat Kit 아웃라인 거동**만 스파이크(§8).
4. **아웃라인 범위 = 전역 라인 우선.** Flat Kit Outline 렌더러 피처로 모든 오브젝트에 잉크 라인.
   #138 선택 강조(상호작용 건물만 도드라지게)는 이 전역 라인 **위에 per-object/레이어**로 얹는 후속 작업.
5. **일단 PC 파이프라인만 적용.** CLAUDE.md "PC/Mobile 양쪽 적용" 규칙의 **명시적 예외**(플랫폼 특정 결정).
   모바일 프리셋(저품질 블러 또는 그레이딩만)은 별도 후속 이슈로 분리.
   ⚠️ **이 예외는 룩 계층에만 적용된다.** 상호작용 아웃라인(§3.6)은 룩이 아니라 **기능**이므로 PC/Mobile 양쪽 필수다.

### 2.1 추가 결정 (2026-07-31)

6. **상호작용 아웃라인 = 스크린 스페이스 실루엣으로 이행 확정.** 현행 인버티드 헐(shell)은 #213에서 **임시 수단**으로 채택한 것이고,
   부품별 테두리·렌더러 512 상한·스무스 노멀 프리베이크 의존·픽셀 룩 비양립이라는 구조적 한계가 있다.
   `InteractionOutline.md` §9에 적힌 MPB 이행안은 **기각**했다(위 4개 중 어느 것도 해결하지 못하고 SRP Batcher 배칭까지 깬다).
   → 작업지시서: **`Docs/Rendering/WIP-OutlineMigration.md`**(임시 문서, 이행 완료 후 삭제).
7. **툰 셰이딩의 목적 = 그림자 단조화로 2D 느낌.** 급격한 셀 컷이냐 소프트 램프냐가 아니라,
   **그림자 계조를 눌러 평면적으로 읽히게 하는 것**이 채택 이유다. §3.4의 "소프트 램프 권장" 가이드는
   이 목적과 충돌하지 않는 선에서 튜닝한다(§8 TODO).
8. **픽셀레이션은 보류 — 실물을 보고 결정한다.** 문서상 확정하지 않는다. 대신 **언제든 켜고 끌 수 있게** 만들고,
   다른 요소가 픽셀레이션 채택 여부에 **의존하지 않도록** 설계한다(§3.7). 특히 아웃라인 두께 규칙이 여기 묶이면 안 된다.
9. **아트 전역 아웃라인은 하지 않는다.** 아웃라인은 **선택·호버 전용**이다. 파급 효과가 크다:
   - Flat Kit `Outline` 피처(전역 스크린 스페이스) **미사용 확정** — 등재하지 않는다
   - Flat Kit `ObjectOutline` 피처도 현행 shell이 유일한 사용처였으므로 이행 완료 시 **제거 대상**
   - #213의 **스무스 노멀 베이커·레지스트리·사본 메시 13개가 전부 용도 폐기** — 인버티드 헐을 아무도 안 쓰게 된다(§3.5)
   - 렌더러 피처 순서에서 아트 라인 항목이 빠져 §3.8이 단순해진다

## 3. 아키텍처 — 레이어 구성

적용 순서 = 의존 순서. 각 레이어는 독립적으로 켜고 끌 수 있어야 한다(튜닝·디버깅·성능 비교).

### 3.1 룩 볼륨 (포스트프로세싱)
- 전역 Volume 프로파일 신설: **Color Adjustments**(채도 +15~25 TBD·대비·따뜻한 톤), **Tonemapping**, **Vignette**(약하게).
- 셰이더 작업 0 — 빌트인 컴포넌트만. 수치는 전부 **튜닝 TBD**(§8).
- ⚠️ `Assets/Settings/DefaultVolumeProfile.asset`에 템플릿 잔재(`CopyPasteTestComponent2` 등 유니티 테스트용
  컴포넌트) 발견됨 — 정리 검토 대상(§8).

### 3.2 틸트-시프트 풀스크린 패스
- **Fullscreen Shader Graph**(스크린 Y 그라데이션 블러) + **Full Screen Pass Renderer Feature**를
  `PC_Renderer`에 등재. Unity 6 URP 내장 기능이라 커스텀 C# 렌더러 피처 불필요 예상(검증 TBD).
- 노출 파라미터: 포커스 중심(스크린 Y 0~1) · 밴드 폭 · 최대 블러 강도 · 샘플 수.
- 경영/전투 공간의 카메라 구도가 달라 밴드 튜닝 값이 다를 수 있음 — 공간별 파라미터 전환 필요 여부 TBD(§8).

### 3.3 라이팅 프리셋
- "책상 스탠드" 콘셉트: 강한 단일 키 디렉셔널 + 또렷한 그림자(PC 소프트 섀도 유지) + 정리된 앰비언트.
- `DayNightLightingController`(WL-020)와 **역할 분리**: 룩 볼륨·틸트-시프트는 **페이즈 무관 전역 상수**,
  낮/밤 전환은 **라이트 색·강도·앰비언트만** 변경. 낮/밤 전환이 룩 볼륨을 건드리지 않는다.
- WL-020의 전역 RenderSettings 변경(앰비언트 모드·스카이박스 교체)과 충돌 여부 확인 필수.

### 3.4 오브젝트 툰 셰이딩 (Flat Kit) — **본진 1차 이관 완료** (2026-08-03)
- Flat Kit 툰(그라데이션 램프) 머티리얼로 오브젝트 셰이딩. Flat Kit 본체는 `Assets/Imported/`(벤더).
- **채택 목적(2026-07-31 확정)**: **그림자 계조를 단조롭게 눌러 화면이 2D로 읽히게** 하는 것.
  전역 아웃라인을 쓰지 않기로 했으므로(§3.5) 오브젝트 분리감도 이 셰이딩이 혼자 감당한다.
- 미니어처 필 유지 가이드: **소프트 램프**(급격한 2단 셀 컷 지양) + **그림자 수용(Receive Shadows) 유지**.
  급한 셀 컷은 "만화" 감성으로 이동해 목표 룩과 어긋난다.

**이관 방식 — 원본 1개 → 사본 1개 + 렌더러 슬롯 교체.** 벤더 무수정 규칙(§5) 때문에 셰이더를
직접 갈아끼울 수 없으므로, 에디터 툴로 사본을 만들어 렌더러의 머티리얼 슬롯만 바꾼다.

| 구성 | 경로 |
|---|---|
| 변환 툴 | `Assets/Scripts/Editor/FlatKitMaterialConverter.cs` — 메뉴 `NorthLand/FlatKit/` (Convert · ReapplyTemplate · Revert) |
| **룩 수치 정본** | `Assets/Settings/FlatKit/CandyLandToon_Template.mat` |
| 원본↔사본 매핑 | `Assets/Settings/FlatKit/CandyLandConversion.json` (원복 근거 · 변환 기록) |
| 사본 머티리얼 | `Assets/Imported/@NorthLand/Materials/CandyLand/FK_*.mat` (아트 저장소) |

사본은 템플릿 파라미터를 물려받고 원본에서 **알베도·표면 상태만** 승계한다. 그래서 룩 튜닝은
템플릿 1개만 고친 뒤 `ReapplyTemplate`을 돌리면 사본 전체에 퍼진다. 툴은 대상 GameObject를
받는 범용이라 전투·기타 에셋에도 그대로 쓴다.

⚠️ **승계를 빠뜨리면 룩이 깨지는 항목** — CandyLand 머티리얼 120개가 **전부 `_Cull: 0`(양면)**이다.
FlatKit 기본값은 Back culling이라 이걸 안 옮기면 지붕·간판에 구멍이 난다. 알파테스트(15개)·
노멀맵(13개)·이미시브(4개)도 함께 승계 대상이다.

**확정 램프 값 (2026-08-03, 본진 스크린샷 비교로 결정 — §8의 "램프 강도 지점" TODO 종결)**

약/중/강 3단계를 같은 축(그림자 어둡기 + 경계 날카로움)으로만 만들어 비교한 결과 **중간값 채택**.
약은 계조가 거의 사라져 형태가 뭉개지고, 강은 셀 컷 경계가 또렷해 "만화" 쪽으로 넘어간다.

| 프로퍼티 | 값 | 의미 |
|---|---|---|
| `_CelPrimaryMode` | 1 (Single) | 셀 1단 |
| `_ColorDim` | (0.58, 0.56, 0.68) | 음영부 색 — 약간 차가운 톤 |
| `_SelfShadingSize` | 0.5 | 명암 경계 위치 |
| `_ShadowEdgeSize` | 0.08 | 경계 부드러움 (0=하드 컷, 0.5=최대 소프트) |
| `_Flatness` | 1.0 | Localized Shading |
| `_UnityShadowMode` / `_UnityShadowPower` | 1 (Multiply) / 0.5 | 빌트인 그림자 수용 — 접지감 유지 |
| `_LightContribution` | 0.6 | 낮/밤 라이트 색이 반영되게(§3.3 역할 분리) |
| `_TextureImpact` | 1.0 | 알베도 100% |

⚠️ **이 룩은 라이팅 전제 두 개에 의존한다** — 둘 중 하나라도 어긋나면 약/중/강 차이가 사라진다.
셰이딩 파라미터를 다시 만지기 전에 이걸 먼저 확인할 것(§3.3 · §8).

1. **앰비언트가 눌려 있어야 한다.** `DayNightLightingController.dayPreset`의 Trilight 값
   (0.6 / 0.65 / 0.75)은 너무 밝아 명암 경계를 메운다. 앰비언트를 끄자 캐스트 그림자가 즉시 나타났다(실측).
2. **`PC_RPAsset`의 `m_ShadowDistance: 50`은 이 월드 스케일에 맞지 않는다.** 마을은 600유닛 폭이고
   게임 카메라는 피사체에서 약 500유닛 거리다 — 그림자가 렌더될 구간이 화면 안에 없다.
   900으로 올리면 픽셀 28.4%가 변한다(실측). **전역 파이프라인 에셋이라 GameScene에도 영향이 가므로 미변경으로 보류**(§8).

- ⚠️ `Assets/Imported/` 원본(Flat Kit 셰이더·샘플 포함) 직접 수정 금지 — 우리 머티리얼은 **Flat Kit 셰이더를 참조하는 별도 머티리얼 에셋**으로 만들어 오브젝트에 적용(벤더 원본 밖).

### 3.5 아트 전역 아웃라인 — **미채택** (2026-07-31)

**전역 잉크 라인은 하지 않는다.** 오브젝트 분리감은 툰 셰이딩의 그림자 단조화(§3.4)로 해결하고,
아웃라인은 **선택·호버 표시 전용**으로 남긴다(§3.6).

이 결정으로 정리되는 것들 — 이행 시 실제로 지울 목록이다:

| 대상 | 처리 |
|---|---|
| Flat Kit `Outline` 렌더러 피처(전역 스크린 스페이스) | **등재하지 않음.** 애초에 레이어 마스크가 없어 대상 지정이 불가능하다(`OutlineSettings.cs` 확인) |
| Flat Kit `ObjectOutline` 렌더러 피처 | 현행 shell이 **유일한 사용처**였다 → §3.6 이행 완료 시 PC/Mobile 양쪽에서 제거 |
| `OutlineSmoothMeshBaker`(에디터 메뉴) · `OutlineSmoothMeshRegistry` | **용도 폐기.** 스무스 노멀은 인버티드 헐 전용 해법인데, 헐을 쓰는 곳이 없어진다 |
| `Assets/Resources/Outline/OutlineSmoothMeshRegistry.asset` · `Assets/Meshes/OutlineSmooth/*.asset`(13개) | 위와 함께 삭제 |

> 나중에 아트 라인을 다시 원하게 되면 Flat Kit `Outline` 피처를 등재하는 것으로 되돌릴 수 있다.
> 단 그때는 §3.8 순서에 "아트 라인 → 틸트-시프트"(초점 밖 라인도 블러) 항목이 다시 들어가야 하고,
> 오쏘 카메라에서의 깊이 임계값 거동을 별도 검증해야 한다.

### 3.6 상호작용 아웃라인 (호버·선택·합성 프리뷰) — #213

**룩이 아니라 기능이다.** 설계·구현 정본은 `Docs/Core/InteractionOutline.md`이고, 여기에는 **룩 계층과 겹치는 부분만** 적는다.

- **현재 상태**: 구현 완료, 단 **인버티드 헐(shell) 방식은 임시**다. `OutlineShell` 레이어(12)를 신설하고
  PC/Mobile 렌더러의 Opaque·Transparent·**Prepass** 마스크 세 곳에서 제외해 아웃라인 패스만 뽑아내는 구조.
- **이행 방향(확정, §2.1-6)**: **스크린 스페이스 실루엣**. 대상 렌더러를 마스크 RT에 슬롯 값(호버/선택/프리뷰)으로 그리고,
  dilate 후 차감해 링을 뽑아 색을 입혀 합성한다. 부품 수와 무관하게 **오브젝트 전체 실루엣 하나**가 나온다.
  → 작업지시서 `WIP-OutlineMigration.md`.
- **아웃라인은 이제 상호작용 전용 신호다**(§3.5 미채택 결정). 상시 라인이 없으므로 화면의 아웃라인은
  100% "선택 또는 호버"를 뜻한다 → 시각 언어 충돌이 없어 **색·두께를 가독성 기준으로만** 정하면 된다.
- **PC/Mobile 양쪽 필수**(§2 결정 5의 예외). PC는 Deferred, Mobile은 Forward라 각각 검증한다.
- **미니맵**: `MinMapCamera`의 cullingMask가 `-1`이라 그대로 두면 미니맵에도 아웃라인이 나온다(#213 T2 미해결). 이행 시 함께 닫는다.

**가려짐(occlusion) 표시 정책** — 스크린 스페이스로 가면서 새로 생기는 선택지다.

오쏘 쿼터뷰라 큰 건물이 뒤의 타워를 가리는 상황이 잦다. 마스크 RT에 대상을 그릴 때 `ZTest`를
`LEqual`로 두면 가려진 표시가 사라지고(현행 동작), `Always`로 두면 앞 오브젝트 위에 실루엣이 겹쳐 그려진다(투시).
**셰이더 상태 한 줄**이라 패스도 코드 경로도 늘지 않는다.

> 현행 shell로는 투시가 **원리상 불가능**하다. 인버티드 헐은 원본 지오메트리가 깊이로 헐 안쪽 면을
> 가려줄 때만 테두리로 보이므로, depth test를 끄면 헐이 통째로 칠해진다(§6.2 박스 프록시가 폐기된 것과 같은 이유).

| 슬롯 | 제안 정책 | 근거 |
|---|---|---|
| 호버 | 가려짐(현행) | 레이캐스트로 맞춘 대상이라 **정의상 보이는 상태**다 — 논점이 아니다 |
| 단일·그룹 선택 | 투시 | 선택한 **뒤에** 카메라가 움직이거나 앞이 가려질 수 있다 |
| 합성 프리뷰 | 투시 | "무엇이 소모되는지 확인"이 기능의 목적인데, 재료 타워가 건물 뒤면 현재는 **안 보인다** |

마스크에 슬롯 값을 인코딩하므로 슬롯별 `ZTest` 분기는 드로우 2회로 끝난다.
**구현 전 확정 불필요** — 만들어놓고 켜보며 정한다(§8 TODO). 전부 투시로 켜면 디오라마 착시가 깨지는 점만 주의.

### 3.7 픽셀레이션 (Flat Kit Pixelation) — **보류 · 실물 확인 후 결정**

문서상으로 정하지 않는다(§2.1-8). **툰 셰이딩까지 올린 화면에 켜고 꺼보며** 판단한다.

> **설계 원칙: 다른 요소가 이 결정에 의존하지 않게 만든다.**
> 특히 아웃라인 두께를 "픽셀 블록의 정수배"로만 정의하면, 픽셀레이션을 껐을 때 근거가 사라진다.
> → 두께는 **스크린 픽셀 단위를 기본**으로 하고, 픽셀 그리드 스냅은 **켜고 끌 수 있는 모드**로 얹는다.
> 이렇게 해야 §3.6 이행이 이 결정을 기다리지 않는다.

채택 여부와 무관하게 아래 **제약은 사실로 확인**되었다.

- `RenderFeatures/Pixelation/FlatKitPixelation.cs` — 순수 포스트프로세스다. `_PixelSize = 1/resolution`으로
  **이미 그려진 컬러 버퍼를 블록 단위로 재샘플링**한다. 기본 `resolution = 320`(긴 변), 기본 이벤트 `BeforeRenderingPostProcessing`(500).
- 1920 화면 기준 블록이 대략 **6px**다. → **폭 1~2px짜리 기하 아웃라인은 블록 양자화에서 깜빡이며 끊긴다.**
  #213이 스무스 노멀까지 구워가며 없앤 "점선 프린지"가 더 나쁜 형태로 돌아온다.
- 따라서 픽셀레이션을 채택하면 **아웃라인 두께는 픽셀 블록의 정수배로 스냅**해야 한다.
  스크린 스페이스 실루엣(§3.6)은 dilate 반경으로 이게 가능하지만, 인버티드 헐은 원리상 불가능하다.
- 틸트-시프트와의 관계는 미검증 — 블러 후 픽셀화인지 픽셀화 후 블러인지에 따라 룩이 크게 갈린다(§8 TODO).

**등재 완료 (2026-08-03) — 기본 off 토글.** 판단은 여전히 팀 컨펌 대기지만, 켜고 끌 수 있는 상태는 만들었다(§2.1-8 설계 원칙).

| 구성 | 경로 / 값 |
|---|---|
| 렌더러 피처 | `Assets/Settings/PC_Renderer.asset`에 `Flat Kit Pixelation` 등재, **`m_Active: 0`(off)** |
| 설정 에셋 | `Assets/Settings/FlatKit/PixelationSettings_PC.asset` — `resolution` 320 · `renderEvent` `BeforeRenderingPostProcessing`(500) |
| Mobile | **미등재** — §2 결정 5(PC 전용)에 따라 `Mobile_Renderer`는 이번 범위 밖 |

⚠️ **줌에 따라 결과가 갈린다 — 단일 `resolution` 값으로는 게임 줌 범위를 못 덮는다.** 블록 크기는
화면 픽셀 기준 고정이라, 줌 아웃하면 오브젝트 대비 블록이 커진다. 본진 실측(1920 기준):

| 프레이밍 | resolution 320 | resolution 480 |
|---|---|---|
| 근접(오쏘 30) | 깔끔한 6px 도트 룩 | 블록이 작아 픽셀감이 약해진다 |
| **게임 기본 줌(오쏘 135)** | **마을이 뭉개져 건물 식별 불가** | 형태 유지, 도트 룩 성립 |

게임 줌 범위가 오쏘 70~300(`CameraController2`)이므로, **채택하면 `resolution`을 오쏘 사이즈에 연동**해야 한다.
고정값으로 가면 한쪽 줌에서 반드시 깨진다. 이건 채택 시 추가 작업량이다(§8).

⚠️ **현행 shell 아웃라인이 픽셀레이션 대상에 들어간다.** `Flat Kit Per Object Outline`이 이벤트 300,
픽셀레이션이 500이라 아웃라인이 블록 양자화를 통과한다 — 위에서 경고한 "깜빡이며 끊김"이 실제로 발생하는 조건이다.
스크린 스페이스 실루엣 이행(§3.6) 후 dilate 반경을 블록 정수배로 스냅해야 해소된다.

### 3.8 렌더러 피처 순서 (단일 진실 원천)

여러 풀스크린 효과가 같은 렌더러에 공존하므로 **순서에 근거를 명시**한다.
아트 전역 아웃라인이 빠지면서(§3.5) 순서가 단순해졌다.

```
틸트-시프트  →  상호작용 실루엣  →  [픽셀레이션]
 (블러 본체)     (UI, 블러 X)      (보류 — 켜면 마지막)
```

| 경계 | 근거 |
|---|---|
| 상호작용 실루엣이 틸트-시프트 **뒤** | 화면 위/아래에서 선택했을 때 **선택 표시가 흐려지면 안 된다**. UI 피드백은 블러 대상이 아니다 |
| 픽셀레이션이 **맨 뒤** | 켤 경우 화면 전체가 같은 그리드에 맞아야 한다. 실루엣만 크리스프하게 남으면 룩이 깨진다 |

> ⚠️ **같은 `RenderPassEvent` 값에 몰아넣고 피처 리스트 순서에 의존하지 말 것.** 동작은 하지만
> 누가 리스트를 재정렬하면 조용히 깨진다. 자작 피처는 이벤트 값을 명시적으로 벌려 잡는다.
> **정확한 이벤트 값 배정은 구현 시 확정 — TODO(§8).**

## 6. 검증 방법

- 테스트 스위트 부재(프로젝트 공통) — **에디터 스크린샷 비교**(`unity-cli screenshot`)로 단계별 전/후를 남기고
  팀 육안 컨펌. 경영/전투 공간 각각 1장 이상.
- 컴파일·씬 에러는 `unity-cli`로 확인(가이드 문서 준수).
- 성능: PC 기준이므로 1차에서는 프레임 예산 측정 생략(모바일 후속 이슈에서 필수).

## 7. 로직/뷰 분리 관점

이 계층은 **전부 뷰**다 — 게임플레이 상태(모델)를 읽지도 쓰지도 않는다. 낮/밤 페이즈 이벤트조차 직접 구독하지
않고(§3.3 역할 분리), 룩 파라미터는 에셋(프로파일·머티리얼)에만 존재한다. 따라서 이 계층의 어떤 변경도
게임플레이 코드 리뷰 대상이 아니며, 반대로 게임플레이 변경이 이 계층을 깨뜨리지도 않는다.
